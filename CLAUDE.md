# Retreat-Modules

A collection of reusable, pluggable gameplay systems (inventory, combat, equipment, crafting, progression, and others), designed to integrate with Retreat's engines and the Forge builder.

This file contains project facts and rules only. Personal preferences belong in `CLAUDE.local.md`.

The root `../CLAUDE.md` also applies here. This file may narrow its scope (see "Status") but not relax its rules; its verification and infrastructure rules apply only once this repository has code that needs them.

## Status

Early stage. Modules: `crates/retreat_module_spawner` (`spawner.rain <count>`, action `rain` on key R), the first module and the template for the next ones; `crates/retreat_module_orbit_camera` (`orbit.start|stop|set_angle`, held actions `orbit_left` / `orbit_right` on the arrow keys), which proves input + camera together (it edits a `GameCamera` and reads `InputActions::is_held` from a `FixedUpdate` system ordered `.after(InputActionSystems)`); `crates/retreat_module_sfx` (`sfx.play <path>`, `sfx.music <path>|off`, action `sfx_beep` on key P), which only spawns the contract's `SoundPlayback` and leaves playback to the engine; `crates/retreat_module_fox_walk` (`fox.set_speed <model> <speed>`), which only writes the contract's `AnimationPlayback` (pure `clips_for_speed` picks and blends Survey/Walk/Run); `crates/retreat_module_highscore` (`score.add|reset|save|load|show`), which saves a versioned document through `SaveStore` and migrates older data (pure `migrate`). the template for the next gameplay modules. `crates/retreat_module_player_spawn` (`spawn.join|solo|leave`) gives each player a character body at a spawn point (it replaces `players` in the arena; never add both), `crates/retreat_module_character_movement` (`movement.input|look`, WASD, mouse, Shift, Space, Ctrl) is the predicted character controller, the template for modules that send input (analog input becomes one command line per tick), and `crates/retreat_module_third_person_camera` (`shoulder.follow|stop|swap`) places a `GameCamera` over a player's shoulder. `crates/retreat_module_character_visuals` derives every player's looks (model, color, facing, clip for idle/walk/run/air, smoothing of other players) on each machine from shared state; the model, clips and colors are `CharacterVisualsConfig`, set by the game: the template for render-only modules. `crates/retreat_module_rifle` (`rifle.fire|reload`) is the hitscan weapon: the template for lag-compensated weapons (client aims and predicts ammo, the authoritative command casts with `cast_ray_at`), `crates/retreat_module_projectile_launcher` (`launcher.fire|reload`) is the rocket weapon: the template for predicted projectiles (`spawn_predicted`, `NetPose`, one-shot `VisualEffects`), and `crates/retreat_module_combat_hud` (crosshair, health, weapons, match clock, scoreboard, winner, kill feed) is the template for HUD modules (pure `hud_view` / `match_view`, engine `UiHud` widgets, numbered lines made from a count). Crawler modules (`../CRAWLER_MODULES_PLAN.md`, phase 1 built 2026-11-27): `crates/retreat_module_account` (`account.login|create|play|logout|delete`, the character list screens) and `crates/retreat_module_areas` (`areas.move|list`); `arena` has the placeholder map `crawler_city` and `player_spawn` has the saved-character mode (`PlayerSpawnConfig::spawn_on_join: false`). ## Layout and decisions

- **What is a module** (FRAMEWORK.md §12, engine/module split): gameplay that is a design choice differing between games, built on engine capabilities. Camera controllers, character controllers, which sound or animation plays when, menus and what gets saved are modules; audio/animation playback, input mapping, storage, UI toolkit, physics simulation and networking are engine capabilities. A module never contains platform-specific (`cfg(target_arch = "wasm32")`) code. When a module needs a capability the contract crate lacks, add a library-neutral entry to `retreat_engine_api` in Retreat-Engine-3D first.
- **One Cargo workspace** (`Cargo.toml` at the root), one crate per module under `crates/`, named `retreat_module_<id>`.
- **Dependencies:** only `bevy` (the exact version the engine pins, `0.20.1`) and contract crates: the engine's `retreat_engine_api` (a git dependency on the public `Retreat-Engine-3D` repository; `Cargo.lock` pins the commit, `cargo update -p retreat_engine_api` takes a newer one) and this repository's `retreat_gameplay_api` and `retreat_weapon_kit`, plus Retreat-CoreSDK crates (`retreat_rng`) and `serde` (for `NetState` components). Never depend on `retreat_engine` (engine internals), on a physics library, or on another module. The manifest checker enforces the list (`retreat_manifest/src/dependencies.rs`, all dependency tables); a new allowed crate is a decision recorded here and added there.
- **Modules never depend on each other.** They cooperate only through contract types.
- **Weapon kit** (`crates/retreat_weapon_kit`, decided 2026-11-26): the behavior every weapon module needs (ammo rules, trigger and aim, command actor, own entry in `Weapons`) is a library that weapon modules depend on, because it is code with queries and casts, which the contract does not hold. A library registers nothing, owns no state and depends only on `bevy` and the two contract crates (`LIBRARY_CRATES` in the checker). Not in CoreSDK: it is shooter code.
- **Gameplay contract** (`crates/retreat_gameplay_api`, decided 2026-11-25): player identity, character size, health, damage, death, respawn, spawn points, score, match phase, view angles, the local player and spawn choice: data, messages, the gameplay system order (`GameplaySystems`) and pure rules about that data; no systems, commands, tuning numbers, physics library or transport; depends only on `bevy`, `retreat_engine_api` and `serde`. A module that uses it calls `add_gameplay_contract` and works when the others are absent. A type goes here only when two modules need it.
- **Shared and module state** (decided 2026-11-25): anything carried between ticks is a `NetState` component (rules: `retreat_engine_api/src/net_state.rs`). The match is one entity named `match` carrying `MatchState` and `Scoreboard` (resources are not rolled back). Messages are not rewound, so each gameplay message is written and read in the same tick: put systems in the contract's `GameplaySystems` sets and read every message every tick. Config times are seconds, turned into ticks with `ticks_from_seconds`. A countdown stored in a component changes every tick and is sent in every broadcast; accepted for the match clock and the health timers.
- **Characters** (decided 2026-11-25): a character's `Transform` is the middle of its body (`CharacterSize::center` / `feet`); its view is the shared `LookAngles`; the player of this machine is `local_player_id(NetLocalClient, SoloPlayer)`, `None` on a server. Anything that reads mouse movement skips replays (`NetReplaying`).
- **Stairs, slopes, respawn** (decided 2026-11-25): `character_movement` adds the engine's `CharacterStepping` to characters and takes `CharacterGround` as the ground (no cast of its own), and on `PlayerRespawned` teleports the character (`PhysicsTeleport`). Its systems run after the gameplay sets, so the tick's spawns and deaths are known on every platform. Health moves only its own dummies.
- **Weapons and death** (decided 2026-11-25, 26): a weapon keeps its entry in the contract's `Weapons` (what a HUD shows) and writes `PlayerFired` (ends spawn protection); it judges hits only where `NetLocalClient` is empty (server or no network). A hit reaches the shooter as a rise of its `hits_landed`. Two weapons use two fire buttons, there is no weapon switch. `health` makes the dead `Intangible`. Shot and explosion looks are engine `VisualEffects` with ids that a replay repeats.
- **Character size** (decided 2026-11-26): the contract resource `CharacterSize` (default a human) is the one size of bodies, hit shape and eyes; a game with smaller characters inserts its own on server and clients. Maps are validated against the default. `character_visuals` owns how death and other players look (`HideVisuals`, `RemoteInterpolation`, `RenderSmoothing`); a weapon rewinds only when it sees another player drawn from the server's past. `RespawnTimer` is a contract component so the HUD can count down.
- **Match flow** (decided 2026-11-26): everything a HUD shows of a match is state on the match entity (`MatchState`, `Scoreboard`, `KillLog`), so late joiners get it; messages do not reach clients. On `MatchRestarted` each module resets its own state (health respawns everyone, which refills weapons and teleports characters; the launcher removes rockets). Player names and colors are the game's `PlayerRoster`, the one source for characters and HUD (decided 2026-11-26).
- **Sounds** (decided 2026-11-26): the module that owns an event plays it (`SoundEvents`, once per id) from its simulation; its config names the cue (`SoundCue`, `None` is silent), the game supplies the files. Ids come from synced counters (shot number, rocket name, life, match number, jumps), so replays do not repeat them; a condition played every tick must be shorter than the engine's 16 s memory of ids. Other players' sounds use the same `event_time` as their looks. The press that captures the cursor does not shoot.
- **Items** (decided 2026-11-26, rules in `retreat_gameplay_api/src/item.rs`): the game's `ItemCatalog` is data (stable string ids, kinds `Ammo` / `Weapon` / `Heal`, a carry limit); `Inventory` (one stack per item, limited slots) is shared state owned by `inventory`; weapons only take their ammunition through `AmmoSource`. Without an inventory weapons are carried and ammunition is unlimited. Ammunition leaves the reserve when a reload finishes. A new life and a new match reset to the starting loadout; a death sends `ItemsLost`. For `loot` (L2): ask `Inventory::room_for`, write `GrantRequested` in `GameplaySystems::Pickup`, read `ItemsLost` in `Drops`; a weapon that must be found is a `Weapon` item in the catalog. Nothing is saved between matches.
- **Loot** (decided 2026-11-26): spots are map data (`PickupSpots`, with a kind), what each kind holds is the game's `LootConfig`. Pickups are bodyless shared entities taken, dropped and removed only by the authoritative machine (taking is not predicted: a pickup vanishes after a round trip; clients count the timers). Walking over one takes it if at least one item fits. A weapon that is found comes loaded, because a weapon's magazine is only emptied while owned and is refilled on every new life.
- **Crawler, phase 1 (decided 2026-11-27, `../CRAWLER_MODULES_PLAN.md`).** Contract additions: `AccountId`, `CharacterId`, `PlayingCharacter` (on a body, shared), `CharacterEntered` / `CharacterLeft` (account to spawning), `MapAreas` with `Area` / `AreaRules` (map data: safe, PvP, tier, max entry level, rectangle, one home area) and `InArea` (shared), record owners `account/<id>` and `character/<id>` (`account_record_owner`, `character_record_owner`). **Server records** are the engine's `RecordStore` (only where the game is decided; never on a client): every module saves only its own part (its module id) of an owner, `account` deletes a character with `delete_owner`, so every module's part goes with it. The manifest capability for records is `storage` (no new capability name). **Routing rule for player requests** (`account/src/commands.rs`, the template for the crawler's request commands): a command a client's button, field or script runs is sent to the server and does nothing else; the client's own prediction of that line does nothing; the server (or a game without a network) decides for the sender; a refusal is the session's notice (no error for a network input, an error in a script). Dev login: the client's hello token is the login name (the engine's `NetClientIdentity`, waiting for it), the server's `DevNameLogin` lets it in as `dev:<lowercase name>`; one connection per player id is the engine's. Names: letters A-Z and digits, 3 to 16, start with a letter, unique per world ignoring case (placeholders in `AccountConfig`). Character ids `<account>-<n>`, numbers never reused. Saved characters (`player_spawn` with `spawn_on_join: false`): the body appears on `CharacterEntered` at the saved place (`player_spawn` part: feet and yaw), or in the home area; saved on `CharacterLeft`, on disconnect (the body leaves at once: decided with the user for the city) and every 30 s (placeholder); a takeover (`NetClientRejoined` in the tick of the leave) hands the body and the session to the new connection. Areas are computed from position every tick on every machine (a pending `PhysicsTeleport` counts); `areas.move` is not allowed from clients (portals come in phase 4). Limits: `MAX_PLAYERS` (8) bodies at once; every client receives every session (names only).
- **Crawler, phase 2: items (decided 2026-11-28, `../CRAWLER_MODULES_PLAN.md`).** Grid items are a second item model beside the arena's stack `Inventory`; `grid_inventory` declares `conflicts = ["inventory"]` (manifest v2, below), so a game selects one. **Contract** (`grid_item.rs`, `container.rs`, `item_world.rs`, `wallet.rs`): game data `GridItemCatalog` (bases with size, equipment slots, two-handed, stack size, rollable, affix pool, icon, color; rarity tiers with weight and affix count; affixes with ranges lifted per item level; `problems()` checked at startup); one entity per item `item_<uid>` with `GridItem` (uid, base, rarity, affixes, level requirement, quantity, size copied from the base) and `ItemPlace` (container, x, y, rotated); containers `container_<kind>_<character>` with `ItemContainer` (id `<kind>/<character>`, kind Bag/Equipment/Chest, layout Grid{columns, rows, visible_rows} or Equipment, owning character, city-only flag, drop command, record owner and part); `CharacterLevel` (body; level 1 when absent, owned by progression in phase 3), `ItemNotice` (body; refusals shown to the player), `Wallet` (`wallet_<character>`), `ServiceSpots` (map data: kind, position, reach). All item state is private to the owning player (engine `NetPrivateTo`, kept current by `sync_item_privacy`), so one component stays far under 1 KB and nobody sees another's bag. **Pure rules** (tested): `fits_in_grid`, `first_free_spot` (row by row, upright then turned), `plan_stack_add`, `check_equip` (the base lists the slot, level reached, slot empty, two-handed needs the off hand empty), `plan_move` (also city-only containers, stacking onto the same base). **Atomic transfers** (`apply_item_transaction`): every item change is computed as data, then all touched containers' records (contract format `{"items": [...]}`, under each container's own owner/part, whichever module moves them) plus extra records (a balance) are written in one `RecordStore` batch, and only then is the world changed; `move_item` is the one move between containers of any modules, `add_to_container` the one way to put new items in. **Uids** (`allocate_item_uids`): blocks of 1000 reserved in record `items`/`item_uids` before use, so a restart never repeats a uid. **Containers exist while used**: `keep_character_containers` opens a playing character's container from its record on the authoritative machine and removes containers whose character stopped playing (no message ordering needed); a chest exists only while open. **Requests** use the routing rule, now one contract function (`route`, `route_request`; `account` uses it too) and `put_request` for every `<module>.put <uid> <x> <y> <0|1>` drop. Modules: `item_rolls` (`items.grant|grant_test|grant_gold`; requirement = item level, placeholder), `grid_inventory` (`bag.put|split`, `GridInventoryConfig` size), `equipment` (`equipment.put`, test level until progression), `town_chest` (`chest.open|close|put`; at a `town_chest` spot in a safe area, closes when the character walks away; rows grow with `spare_rows` below the lowest item, so it has no limit; `shared_by_account` switch), `wallet` (`wallet.deposit|withdraw` at a `deposit` spot; bag and balance in one batch), `container_ui` (key `I`, windows through the engine's `UiGrids`, tooltips, notices; render-only; `assert.items_visible` proves privacy on a client). Test commands (`items.*`, `equipment.test_level*`) reach the server from clients only when the game turns `test_commands` on. **An item refusal is the player's `ItemNotice`, never a command error** (unlike `account`): a refused drop or deposit is game feedback, also in a script, which asserts it with `assert.item_notice <text>`; only a request without a playing character is an error. Gear gives no stats yet (the stat list is open for phase 3); dropping items on the ground comes with world loot (phase 3).
- **Manifest v2 (decided 2026-11-28):** adds the optional key `conflicts` (module ids a game must not select with this one); everything else is v1, and v1 manifests stay valid. The checker reads 1 and 2; `conflicts` in a v1 manifest is an error. The resolver refuses a selection that holds both sides of a conflict (declared on either side).
- **Looks are not shared state:** a render-only module derives them from synced components every frame (an entity a replay respawns gets them again) and never changes the simulation. Assets belong to the game (paths in the module's config, credits in the game's `assets/CREDITS.md`).
- **Tuning values** (decided 2026-11-25): a module with numbers exposes a `<Name>Config` resource whose `Default` holds the numbers; a game overrides it by inserting the resource before adding the plugin. Manifest v1 `config` stays empty; declaring config in the manifest needs v2.
- **A module is a Bevy plugin** (`<Name>ModulePlugin`) that registers its commands with `AppCommandExt::register_command`. Every user-visible action is a command (`area.verb`, area = module id). Randomness comes only from `SimulationRng`. Physics objects are `retreat_engine_api::PhysicsBody` descriptions on named root entities (the engine creates the real bodies in a deterministic order).
- **Manifest v1 (frozen; v2 below adds `conflicts`):** `[package.metadata.retreat]` in each module's `Cargo.toml`, read by Retreat-Forge through `retreat_manifest`. Keys (all required unless noted): `manifest_version = 1`; `id` (`[a-z][a-z0-9_]*`, crate is `retreat_module_<id>`); `display_name`; `summary`; `plugin` (`<crate>::<PluginType>`); `commands` (ids registered with `register_command`, each `area.verb`, may be empty); `actions` (optional; ids registered with `register_action`); `requires` (engine capabilities, only names from `retreat_manifest::capabilities::CAPABILITIES`: `animation audio camera input networking physics storage ui`, list version 1; it moves into `retreat_engine_api` when the engine publishes one); `engine_api` (semver requirement on `retreat_engine_api`, e.g. `"0.1"`); `targets` (`"native"`, `"wasm"`); `network_role` (`"server"`, `"client"` or `"both"`; required exactly when `requires` has `networking`); `config` (optional, reserved placeholder, must be an empty table). Unknown keys are errors. Ids of modules, commands and actions are unique across modules. Changing the schema means a new `manifest_version`.
- **Validator and resolver** (pure, no Bevy, native + wasm32): `crates/retreat_manifest` (parser, capability list, `check_manifests` binary) and `crates/retreat_resolver` (`resolve(selection, manifests, engine_version) -> Plan | ResolveError` with every problem in plain language). CI runs `cargo run -p retreat_manifest --bin check_manifests .`; it fails when a manifest and the source disagree. A new way of registering commands or actions needs a form added to `source_scan.rs` with a test. Adding a module: add its crate to the workspace `members` and a valid manifest, then run the checker.
- **engine_api versioning and distribution:** crates are distributed as tagged git releases (no crates.io, no registry). `retreat_engine_api` is versioned with semver in its own tag stream, and a major bump breaks every module: all modules must be updated and released against it. Minor/patch bumps stay compatible with every module whose `engine_api` range allows them. Scope is 3D only (2D is out of scope).
- **Test targets** (decided 2026-11-26, keeps `target/` small): a crate without unit tests sets `[lib] test = false` and `doctest = false`.
- **Tests use only Bevy and the contract crates** (`MinimalPlugins` + `CommandRegistry` + `SimulationRng` + the plugin, run commands with `run_command_line`). The rendered and simulated result is checked in the engine sandbox, which adds the module (`Retreat-Engine-3D/scripts/verify/module_<id>.cmds`) or in a game that loads it (arena: `Retreat-Arena/scripts/verify/arena_map.cmds`). Modules with several test files keep them in `tests/<id>/main.rs`.
- **CI** (`.github/workflows/ci.yml`): fmt, clippy with warnings as errors, tests, the manifest check over all modules, and a `wasm32-unknown-unknown` check.

## Rules

- Each module is an independent crate with a manifest (capabilities, dependencies, compatibility, configuration). Modules depend on `Retreat-CoreSDK` and the engine's public API / contract crates, never on each other and never on engine internals.
- **Shared generic helpers:** check `Retreat-CoreSDK` first. A helper stays inside the module that first needs it; when a second module needs it, move it to CoreSDK instead of copying it. What belongs in CoreSDK, and what does not, is defined in `../Retreat-CoreSDK/CLAUDE.md`. Shared gameplay concepts (items, damage, health) go in contract crates, not in CoreSDK and not duplicated across modules.
- Modules must build for both native and `wasm32-unknown-unknown`.

## Working rules

- Keep the initial implementation as simple as reasonably possible.
- Do not modify sibling repositories from this one without being asked.
- Write documentation and code comments in English.
